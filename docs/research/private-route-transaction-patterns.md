## What one transaction means

Pinned LEZ accepts one public transaction message with one root program, account list and instruction, or one privacy-preserving transaction with a proof and the resulting public/private state changes. A root program can return chained calls. The runner visits them in order, finishing each child's descendants before the next sibling. These are program calls within one transaction, not separate submissions. A privacy-preserving transaction can touch public and private accounts together; its public pool changes remain public. [Public message][P-public-message], [private message][P-private-message], [private runner][P-runner], [official transfer behavior][D-native].

The pinned public runner accumulates a temporary state diff. The private proof circuit checks the complete graph, including matching each call's pre-state to the prior post-state, program identity, authorization and execution rules. State validation then checks the proof, current public pre-states, signatures, nonces, commitment freshness and nullifiers. Only a validated diff is applied. The sequencer skips a user transaction that fails validation. Thus the pinned code supports all-or-nothing application state changes across a valid call graph. A failed proof has no trade to undo. This is source evidence for the mechanism, not a successful test of this launchpad route or a guarantee about network finality and wallet storage. [Public/private diff validation][P-diff], [private graph validation][P-graph], [state commit boundary][P-state], [sequencer validation][P-sequencer].

Calling three WalletCore methods in succession creates three transaction messages and three commit points. Submitting them together, or approving them once, does not make them atomic. The inspected WalletCore and FFI generic methods each accept one root program/instruction; no separate atomic multi-transaction batching API was established. A future SDK could build an atomic batch by constructing one call graph, but it must still obey that graph's rules and budget. Any claim of another batch mechanism needs its exact API, executor code and failure test. [WalletCore submission][P-wallet-send], [generic FFI][P-ffi], [LP-0021 requirements][L-provider].

## Native transfers, custom assets and control

Shield and deshield are transfer directions across the public/private account boundary. Pinned WalletCore exposes native deshield and shield methods, and separate token-program deshield and shield methods. They call the ordinary transfer programs using different account identities. No dedicated launchpad privacy contract is needed merely to transfer across that boundary. No inspected stock instruction transfers both custom token data and native gas balance in one operation; these can instead be separate calls in one graph, from correctly owned and authorized sources. [Native deshield][P-native-deshield], [native shield][P-native-shield], [token directions][P-token-facade], [native instruction][P-native-instruction], [token transfer][P-token-transfer].

A spent private source needs the wallet's current account state, nullifier secret and membership proof. A fresh foreign private destination can be initialized using NPK, VPK and an identifier, without the recipient signing. An existing private destination cannot be treated as a fresh default account: the wallet needs its current state and update authority. The pinned wallet marks owned private accounts authorized; a foreign identity uses an unauthorized default account and encrypts for its VPK. The circuit deliberately allows an unauthorized private initialization claim. A bare private AccountId does not supply the required encryption or spending information. [Identity preparation][P-account-manager], [private witness construction][P-private-identities], [owned state preparation][P-owned-private], [private claim rule][P-private-claim], [official receiver procedure][D-receive].

The public transient account needs a signing key for this route. Setting `is_authorized = true` in guest code cannot replace that signature. ATA spending uses the owner's authorization plus the ATA program's PDA seed. The local client creates and saves the transient key before submission, but requires both private endpoints to resolve in its own wallet; it does not expose the platform's foreign-recipient route here. Public and private authorization propagation also differs in the pinned runners, which explains the local `Instruction::Private` wrapper. [Public authorization checks][P-diff], [ATA transfer][P-ata-transfer], [local client, lines 131-180](../../crates/launchpad-client/src/lib.rs#L131-L180), [local mode handling, lines 38-49 and 249-252](../../crates/curve-core/src/dispatch.rs#L38-L49), [private authorization tracking][P-private-auth].

## Two problems in the imported route

### Total-call budget

The pinned constant is 10. The private proving helper checks `counter >= 10` before every execution and counts the root. It permits 10 total executions, rejects the 11th, and counts siblings as well as descendants. Despite the error name `MaxChainedCallsDepthExceeded`, this is not a nesting-depth limit. There is also an off-by-one difference: the pinned public runner and private circuit validator use `counter <= 10`, so those paths allow 11 total executions. The ordinary WalletCore private proving path is constrained by the stricter 10-total helper. [Private runner, lines 80-124][P-runner], [public runner, lines 124-132 and 298-310][P-diff], [private validator, lines 124-197][P-graph], [constant][P-constant].

The fresh-ATA private-buy graph needs 14 executions: root 1 + native funding 1 + two ATA creations with token initialization 4 + collateral deshield 1 + curve swap with two ATA/token transfer pairs 5 + purchased-token ATA/token re-shield 2. The next execution after the first 10 is the pool-output ATA transfer, before re-shield is reached. The local guest test expects the limit error, not a successful purchase; it was read, not rerun. [Local router, lines 108-189](../../methods/guest/src/bin/private_buy.rs#L108-L189), [local swap, lines 562-585](../../crates/curve-core/src/dispatch.rs#L562-L585), [ATA creation][P-ata-create], [ATA transfer][P-ata-transfer], [local rejection assertion, lines 401-410](../../crates/launchpad-client/tests/private_authority.rs#L401-L410).

### Native gas-source ownership: static incompatibility

The normal client selects the distinct token and authenticated-transfer program artifacts. The router requires its sole private source to be token-owned, clones that same source, and asks authenticated-transfer to debit its native balance. The source owner is never changed or remapped; only the transient recipient's predicted owner changes. Authenticated-transfer debits the sender's balance without changing its owner. Pinned `validate_execution` rejects a native balance decrease if the executing program is not the account owner, with no private-account exemption. This is a static incompatibility in the imported funding call. It still needs a small executable test; it is not a second observed test failure. [Local client, lines 138-150 and 182-190](../../crates/launchpad-client/src/lib.rs#L138-L150), [local source and gas call, lines 61-114](../../methods/guest/src/bin/private_buy.rs#L61-L114), [program artifacts][P-artifacts], [native debit][P-native-debit], [owner validation, lines 700-709][P-owner-rule].

The host proves individual calls before the final graph-validation circuit runs. Its call-limit return occurs first, so the existing rejection test cannot establish that the gas call passes graph validation. A separate authenticated-transfer-owned private gas source is one candidate repair. Changing the graph budget alone does not repair ownership. These are implementation problems; neither proves that the general single-transaction design is unsupported. [Private runner, lines 87-148][P-runner], [circuit execution check][P-graph].

## Can a single transaction be smaller?

Flattening the six siblings does not help a total-call limit. Removing the curve's `Private` enum wrapper saves no execution. The router cannot directly debit another program's token holding or pool state, and it cannot mint the ATA program's PDA authority. Simply dropping both ATA creation calls conflicts with the existing curve's participant ATA checks and the fresh public accounts' claim requirements. [Owner rules][P-owner-rule], [ATA creation][P-ata-create], [local participant/pool ATA checks, lines 532-555](../../crates/curve-core/src/dispatch.rs#L532-L555).

A testable alternative is to let a private-specific swap path use fresh, independently signed ordinary token holding accounts for the participant, while keeping pool custody in its existing ATAs. Direct token transfers can initialize a default signed recipient. A candidate graph would count 8: router 1, native funding 1, collateral deshield 1, curve 1, direct participant-to-pool token transfer 1, pool-output ATA/token transfer pair 2, direct purchased-token re-shield 1. This removes the two ATA-create pairs and both participant ATA wrappers; the existing curve cannot use these ordinary holdings unchanged. It requires changed account validation, signatures for the participant holdings, correct token definitions, a separate compatible gas source and exact predicted state snapshots. It is a design candidate, not a demonstrated simplification or an instruction to implement it. One direct collateral refund and one native return would bring this candidate to the pinned helper's 10-total limit, with no spare call. [Default token recipient initialization][P-token-transfer], [claim authorization][P-private-claim], [local swap graph, lines 488-585](../../crates/curve-core/src/dispatch.rs#L488-L585).

Pre-initialized ATAs can reduce calls, but prior setup is another transaction and weakens the fresh single-use-account premise. Moving final token output directly to a private recipient could remove an intermediate account, but requires changes to the curve's account contract and a proof of equivalent custody and authority checks. Neither option is verified here. [ATA no-op creation][P-ata-create], [local output-account check, lines 538-543](../../crates/curve-core/src/dispatch.rs#L538-L543).

## Two-option comparison

The three-transaction option means T1 deshield/fund and prepare accounts, T2 public trade, T3 re-shield/cleanup. It can still need small coordinating guests: stock wallet facades do not make gas plus collateral funding one stock operation. With a separate correctly owned gas source, the current funding/setup subtree would count 7 executions, the public swap 5, and a cleanup root with launch-token ATA transfer, collateral ATA transfer and native return 6. These counts suggest a route to three commit points; they are not executed tests. Sources for the count are the [local router](../../methods/guest/src/bin/private_buy.rs#L108-L175), [local swap](../../crates/curve-core/src/dispatch.rs#L562-L585), [ATA transfer][P-ata-transfer] and [native transfer][P-native-debit].

| Concern | One combined transaction | Three independent transactions |
| --- | --- | --- |
| Failure boundary | Funding, trade and re-shield application state commit together after validation. | Each stage commits separately. T2 failure leaves T1 funds public. T3 failure leaves purchased tokens public. |
| Price and state | Private proof construction still has a stale-state risk before inclusion. | Can get a fresh quote after T1, but T2 can still see changed price, fee rate or lifecycle. A trade failure needs a recovery choice. |
| Work per submission | One private proof for the entire graph and one transaction outcome; current graph fails its budget. | Two smaller private graphs around a public trade; more submissions, stage tracking and synchronization. No measured latency or cost comparison exists here. |
| Public exposure | Pool deltas and final public account states are visible in one transaction. | Funding amounts and intermediate balances remain public between transactions, potentially for an unbounded time. |
| Linkage | Public accounts and effects occur together in one transaction. | Reusing the transient account and its ATAs links the stages publicly even though the hashes differ. Splitting alone does not hide the trade. |
| Recovery and approval | No accepted separate-stage fallback in ADR 0018. Unknown outcomes still need reconciliation. | Allows retry of a failed re-shield without repeating the trade, but needs saved keys, stage receipts, approval and collateral/token/gas recovery rules. |

The failure rows follow the [pinned state commit boundary][P-state]. Price limits come from the [local exact-output swap, lines 79-109](../../crates/curve-core/src/pool_swap.rs#L79-L109); private inclusion validates the proof against current public pre-states, so a pool change can invalidate a proof even if the price stays within the cap. Public visibility follows the [private message fields][P-private-message] and [official native-transfer tutorial][D-native]. More stages do not establish either a fee saving or a privacy gain.

## Remainders, gas and privacy

The imported router deshields `max_collateral_in`, while the swap spends `settlement.amount_in`. It only requests re-shield of the purchased launch tokens. If that graph succeeded, `max_collateral_in - amount_in` would remain in the public collateral ATA; native funding would also have no router return call. The current graph fails before commit, so these are prospective leftovers, not funds stranded by this test. The router's `gas_reserve` funds a native balance; it does not calculate an execution fee or refund. Treat it as local funding policy, not a verified platform gas estimate. Token and native leftovers are separate balances and may need separate private targets under the pinned ownership model. [Local deshield/re-shield, lines 134-175](../../methods/guest/src/bin/private_buy.rs#L134-L175), [local actual input, lines 562-567](../../crates/curve-core/src/dispatch.rs#L562-L567), [token transfer][P-token-transfer], [native owner rule][P-owner-rule].

One combined route could deshield the exact required input, retaining the cap as a limit, or add a remainder refund based on the same quote and state. The pinned chained-call format supplies complete pre-state snapshots rather than returning a live child result to the router. Refund construction must therefore compute and verify the exact same amount; merely returning the cap is unsafe. In three stages, T3 can read the actual confirmed remainder, but can fail or be abandoned. Gas-return policy must retain enough funds for recovery where fees apply. No automatic refund follows from calling a route private. [Pinned chained execution and state consistency][P-runner], [private graph checks][P-graph], [local quote and spend](../../crates/curve-core/src/pool_swap.rs#L79-L109).

A combined private message publishes public account IDs, final public states, commitments, nullifiers and encrypted private post-states. It does not publish the private account IDs or ordinary instruction calldata in that message. Pool reserve changes still reveal trade effects. Three stages additionally expose the funded balance and purchased holding between commits. Fresh public accounts reduce address reuse but do not hide a transaction's public co-occurrence, amounts or timing. Encrypted records carry view tags and lengths; this inspection does not establish resistance to traffic analysis, key reuse, RPC logging or a wallet provider that sees the proposed action. [Message fields][P-private-message], [private identity preparation][P-private-identities], [view-tag scanning][P-wallet-sync], [official visibility statement][D-native].

## WalletCore, LP-0021 and retries

WalletCore already constructs witnesses, proves a graph, builds a message, signs public accounts and sends one transaction. The on-chain router composes calls and validates route-specific rules; a provider cannot change the executor's budget or make separately committed stages roll back together. LP-0021 is marked open and specifies account selection, explicit approval, human-readable call effects, state persistence and testnet tests. It does not define a final provider method for this multi-program private graph, atomic batching or account-specific retry behavior. A provider implementation and integration test must establish those features. [WalletCore pipeline][P-wallet-send], [LP-0021 functionality/usability/reliability][L-provider].

Pinned `send_privacy_preserving_tx` returns a hash and shared secrets after RPC submission; it does not itself persist the resulting private states. WalletCore can decode confirmed results, or sync confirmed blocks, decrypt private post-states and save state plus sync height. The local private-buy client saves the transient key before sending and discards the returned shared-secret vector; it does not confirm inclusion or perform private-state synchronization in that method. Normal wallet scanning can recover decryptable updates, but this path still needs restart and lost-response tests. [Result decode][P-wallet-decode], [block sync and persistence][P-wallet-sync], [local submission, lines 131-135 and 194-206](../../crates/launchpad-client/src/lib.rs#L131-L135).

An RPC timeout means the result is unknown. It does not prove failure. The same spent private state cannot be accepted twice: pinned validation rejects used nullifiers and old public signing nonces. However, reconstructing a new trade after synchronization can spend a new state with new nonces and execute a second purchase. The inspected route has no application-level trade-intent identifier. Do not automatically turn an unknown outcome into a fresh trade. Save enough non-secret intent and transaction identity information to query the original outcome, synchronize, and distinguish retrying the same submission from requesting another trade. Three stages also need to record which stage committed so recovery does not run T2 twice. Exact resubmission and confirmation behavior remains a provider/RPC test gap. [Replay checks][P-state], [private transaction signatures/nonces][P-diff], [transaction hash][P-tx-hash], [local instruction fields](../../crates/private-flow-core/src/lib.rs).

## Current upstream is different

At `c31a6b...`, accounts use program-selected shards and a native-token implementation with planned debit/credit effects. WalletCore takes `AccountMention` and `ProvingInput`, not the pinned account/output shapes. The shared traversal retains `MAX_NUMBER_CHAINED_CALLS = 10` but rejects only when `prepared_calls > 10`: it permits the root plus 10 descendants, 11 total. A source test checks 10 sibling calls succeed and 11 siblings fail. This is code/test-source evidence for that revision, not a claim that an unchanged 14-call route fits or that the local ABI and authorization scheme remain compatible. [Current native implementation][N-native], [current WalletCore][N-wallet], [current budget constant][N-constant], [current traversal][N-traversal], [current budget test][N-budget-test].

Current upstream also has public transaction fee reservation, action execution and refund. A failed charged public action reverts its application effects but still pays fees and advances replay nonces. Unused fee reserve returns to the public payer; this is different from re-shielding surplus gas or collateral. Admission checks the payer's existing balance before execution, so funding a fresh public payer inside its own charged transaction is insufficient. The inspected current sequencer test explicitly says private transactions are uncharged and unscreened. These facts limit any blanket claim that failure changes nothing or that private-route gas behaves like current public fees. Deployment/version compatibility and future private fees remain unresolved. [Current fee settlement][N-settlement], [current admission][N-admission], [current private-fee exemption test][N-private-fees], [current fee fields][N-fees].

## Evidence gaps and conditional recommendation

| Evidence class | What is established | What still needs a small executable probe |
| --- | --- | --- |
| Pinned code and local test source | All-or-nothing validated application diff; total-call counting; 14-call route and limit-error assertion; static gas-source ownership mismatch. | Corrected funding from compatible sources; a complete successful buy; late swap/re-shield failure with unchanged pool, public balances, commitments and nullifiers. |
| Simplification calculation | A signed ordinary-holding route could remove six calls without changing pool ATA custody. | Signature/owner/definition checks, correct snapshots, exact-input funding or cap remainder refund, gas cleanup, and actual budget at the chosen revision. |
| Official docs and prize | Public/private transfers, fresh recipient keys, public effects, and wallet approval/persistence requirements. | Provider support for all accounts and dependencies, understandable approval of the full graph, available gas policy, confirmation and failure semantics. |
| Client state and retry code | Keys can be saved; private updates can be decrypted and synced; nonce/nullifier replay checks exist. | Drop the RPC response after acceptance; restart before sync; resubmit identical bytes; attempt a rebuilt request; verify one purchase and recoverable balances. |
| Three-stage design | Each stage can fit a smaller graph and has its own commit boundary. | T1 committed/T2 rejected; T2 committed/T3 rejected; fresh quotes after T1; saved-key cleanup of collateral, purchased tokens and gas; safe recovery after long delay. |

Keep one combined transaction as the preferred candidate if the user requires that a purchase cannot complete without re-shield. First test a smaller graph with correct gas-source ownership and a deliberate late failure. Do not ship or approve the imported route on the strength of its current test. Choose three independent transactions only if the user accepts an already completed trade while re-shield is pending, public funds between stages, and a supported recovery flow. That would require reconsidering ADR 0018, not silently adding a fallback.

The user must choose the required failure/privacy experience and whether slower staged recovery is acceptable. Tests must settle platform execution, budget, funding ownership, refund accounting, wallet approval and restart/retry safety. In plain terms: one transaction keeps the purchase and re-shield together; three smaller transactions let each step finish on its own, but the user can be left with public funds when a later step fails.
