## Clock documentation

Open first-party documentation PR [#1001](https://github.com/logos-blockchain/logos-execution-zone/pull/1001) includes a developer guide that says, verbatim, "The clock runs last in a block, so transactions in block N see the time of block N-1." It also says that validity windows are checked against the block being built and recommends windows for simple deadlines. The guide was an unmerged draft at review. Source: [frozen draft, clock and windows](https://github.com/logos-blockchain/logos-execution-zone/blob/616256b9c9efd2c28d4f7683b7b5d2348df7314e/docs/lez-guide/src/build/system-programs.md#L28-L104).

The original merged clock PR explicitly specifies a mandatory clock invocation as the last transaction of each block. Thus, the ordering was a stated implementation choice, not an accidental result found only in current code. That PR does not explain why the tick must be last rather than first. Source: [PR #403 description](https://github.com/logos-blockchain/logos-execution-zone/pull/403).

## Three different meanings of time

Code-verified: LEZ `Timestamp` is Unix milliseconds. The producer captures its local UTC clock while building a block. User transactions run before the fee transaction and clock tick. Followers apply user transactions using the block header timestamp for validation, then apply the fee transaction and clock tick. Therefore, clock assertions and timestamp validity windows can use different timestamps within one transaction: the saved clock value and the current inclusion block's header time. Sources: [timestamp type](https://github.com/logos-blockchain/logos-execution-zone/blob/1806e873ea2ac0e1b608aa7cf2f9b6e1fb12db21/lee/state_machine/core/src/lib.rs#L43-L44), [pinned producer](https://github.com/logos-blockchain/logos-execution-zone/blob/578ce58a71b79c49d48e97e51c520bf71f0252d9/lez/sequencer/core/src/lib.rs#L1720-L1755), [pinned block tail](https://github.com/logos-blockchain/logos-execution-zone/blob/578ce58a71b79c49d48e97e51c520bf71f0252d9/lez/sequencer/core/src/lib.rs#L1920-L1938), [current follower application](https://github.com/logos-blockchain/logos-execution-zone/blob/1806e873ea2ac0e1b608aa7cf2f9b6e1fb12db21/lez/chain_state/src/apply.rs#L149-L258).

Code-verified: the three clock accounts are `/LEZ/ClockProgramAccount/0000001`, `/LEZ/ClockProgramAccount/0000010` and `/LEZ/ClockProgramAccount/0000050`. They store both block ID and timestamp. The every-block clock advances at the block tail; the others update at multiples of 10 and 50. During user execution in block N, the every-block clock therefore holds block N-1's timestamp; a coarse clock can be older. These are separate system clock accounts, not launchpad namespaces. A block interval is not a maximum wall-clock age. Sources: [clock IDs and data](https://github.com/logos-blockchain/logos-execution-zone/blob/1806e873ea2ac0e1b608aa7cf2f9b6e1fb12db21/lez/programs/clock/core/src/lib.rs#L1-L62), [update schedule](https://github.com/logos-blockchain/logos-execution-zone/blob/1806e873ea2ac0e1b608aa7cf2f9b6e1fb12db21/lez/programs/clock/src/main.rs#L22-L75), [explicit draft explanation](https://github.com/logos-blockchain/logos-execution-zone/blob/616256b9c9efd2c28d4f7683b7b5d2348df7314e/docs/lez-guide/src/build/system-programs.md#L28-L53).

Code-verified: in the pinned and current actor API, the clock has `Tick`, `Record` and `AssertTimestamp`; it has no timestamp-returning read message. `AssertTimestamp` tests the clock actor's saved time against the inclusive range `[at_least, at_most]`. The first-party cooldown example accepts a proposed time in its message, uses it in its own calculation, then sends an exact equality assertion to the canonical clock actor. This binds caller-supplied time to clock state; merely passing a time does not bind it. Sources: [clock API](https://github.com/logos-blockchain/logos-execution-zone/blob/578ce58a71b79c49d48e97e51c520bf71f0252d9/lez/programs/clock/core/src/lib.rs#L24-L46), [assertion implementation](https://github.com/logos-blockchain/logos-execution-zone/blob/1806e873ea2ac0e1b608aa7cf2f9b6e1fb12db21/lez/programs/clock/src/main.rs#L67-L74), [cooldown example](https://github.com/logos-blockchain/logos-execution-zone/blob/1806e873ea2ac0e1b608aa7cf2f9b6e1fb12db21/test_programs/guest/src/bin/cooldown.rs#L40-L64).

## Proof binding and the documented rationale

Verified maintainer explanation: in the original clock PR, `schouhy` explains the three update rates: "clock accounts are public. A proof for a private tx reading from it will become invalid the moment it gets updated and value used in proof differs from onchain state." Slower clocks let programs that need less precision "improve private execution experience". This is a direct reason for coarse clocks, not a direct explanation for every detail of clock ordering. Source: [maintainer comment on PR #403](https://github.com/logos-blockchain/logos-execution-zone/pull/403#issuecomment-4185237964).

Code-verified for v0.2: private transaction verification reconstructs public input accounts from the current public state before checking the proof. It does not select an arbitrary historical public clock snapshot for the user. Historical private commitment membership must not be confused with permission to use old public clock state. Source: [v0.2 validation](https://github.com/logos-blockchain/logos-execution-zone/blob/a58fbce2ff48c58b7bb5001b1a27e64b9596ee3a/lee/state_machine/src/validated_state_diff.rs#L405-L436).

Verified source statement and current code: actors change this constraint. Open PR [#988](https://github.com/logos-blockchain/logos-execution-zone/pull/988) says, "With actors a pptx depends on the clock's answers, not on its state". Current actor settlement verifies the proof and runs the public part against current public state, using its proof-bound message boundary. A clock assertion can therefore remain valid across ticks if its condition still holds. An exact equality assertion still fails when the saved clock time changes. Sources: [#988 rationale](https://github.com/logos-blockchain/logos-execution-zone/pull/988), [pinned private settlement](https://github.com/logos-blockchain/logos-execution-zone/blob/578ce58a71b79c49d48e97e51c520bf71f0252d9/lee/state_machine/src/validated_state_diff/mod.rs#L308-L356), [current clock condition](https://github.com/logos-blockchain/logos-execution-zone/blob/1806e873ea2ac0e1b608aa7cf2f9b6e1fb12db21/lez/programs/clock/src/main.rs#L67-L74).

Open proposal, not current behavior: #988 would replace the three accounts with one clock actor, round time down by caller-selected granularity, and add block-ID assertions. It requires a regenesis and rebuilds. The proposal is still open, and these features are absent from `v0.4.0-rc1`; do not use them as the pinned API. Sources: [proposal status and changes](https://github.com/logos-blockchain/logos-execution-zone/pull/988), [current message enum](https://github.com/logos-blockchain/logos-execution-zone/blob/1806e873ea2ac0e1b608aa7cf2f9b6e1fb12db21/lez/programs/clock/core/src/lib.rs#L24-L39).

Inference: putting the tick after users lets a v0.2 proof based on the latest every-block clock survive into the next block's user phase. Ticking first would change that public input before verification. This fits the documented proof problem, but I found no maintainer statement that gives this as the reason for tail ordering, or explains why actors retain that ordering. Sources supporting the inference: [original ordering](https://github.com/logos-blockchain/logos-execution-zone/pull/403), [maintainer proof explanation](https://github.com/logos-blockchain/logos-execution-zone/pull/403#issuecomment-4185237964), [v0.2 verification](https://github.com/logos-blockchain/logos-execution-zone/blob/a58fbce2ff48c58b7bb5001b1a27e64b9596ee3a/lee/state_machine/src/validated_state_diff.rs#L405-L430).

## Inclusion-time deadlines are a separate API

Code-verified: the pinned actor response supports `.timestamp_window(..end_ms)` and `.timestamp_window(start_ms..)`. Finite two-sided ranges use `.try_timestamp_window(start_ms..end_ms)`. Windows have an inclusive lower bound and exclusive upper bound, and handlers' windows are intersected. Public settlement checks the resulting window against its supplied block context; private settlement also checks the proof's validity window against that context. This permits inclusion-time gates without a clock read. Sources: [response builders](https://github.com/logos-blockchain/logos-execution-zone/blob/578ce58a71b79c49d48e97e51c520bf71f0252d9/lee/state_machine/core/src/program/mod.rs#L476-L499), [range semantics](https://github.com/logos-blockchain/logos-execution-zone/blob/1806e873ea2ac0e1b608aa7cf2f9b6e1fb12db21/lee/state_machine/core/src/program/mod.rs#L588-L626), [pinned private check](https://github.com/logos-blockchain/logos-execution-zone/blob/578ce58a71b79c49d48e97e51c520bf71f0252d9/lee/state_machine/src/validated_state_diff/mod.rs#L308-L319), [pinned settlement check](https://github.com/logos-blockchain/logos-execution-zone/blob/578ce58a71b79c49d48e97e51c520bf71f0252d9/lee/state_machine/src/validated_state_diff/mod.rs#L430-L445), [draft explanation](https://github.com/logos-blockchain/logos-execution-zone/blob/616256b9c9efd2c28d4f7683b7b5d2348df7314e/docs/lez-guide/src/build/messages.md#L172-L182).

Verified first-party application evidence: `lez-programs` AMM guest handlers already attach `.with_timestamp_validity_window(..deadline)` to outputs. SPEL exposes that older output API and passes it through its generated dispatcher. The AMM's QML JavaScript request path also supplies `deadlineMs`; some current UI flows use `u64::MAX`, so they demonstrate transport, not a useful user timeout. These sources do not establish actor compatibility for SPEL or the AMM. Sources: [AMM guest](https://github.com/logos-blockchain/lez-programs/blob/6674d7833a8f5d618126d992eed5cfe21bd86ba4/programs/amm/methods/guest/src/bin/amm.rs#L174-L205), [SPEL window API](https://github.com/logos-co/spel/blob/c6f73ce21e4805f8430f03afdbdedf0b7e479a5e/spel-framework-core/src/types.rs#L72-L108), [generated pass-through](https://github.com/logos-co/spel/blob/c6f73ce21e4805f8430f03afdbdedf0b7e479a5e/spel-framework-macros/src/lib.rs#L426-L448), [QML request](https://github.com/logos-blockchain/lez-programs/blob/6674d7833a8f5d618126d992eed5cfe21bd86ba4/apps/amm/qml/components/liquidity/RemoveLiquidityDialog.qml#L195-L208).

## Design options reviewed

These options follow from the cited APIs. They do not replace the selected design in ADR 0026 or establish a completed integration.

- For a fixed-price sale that must reject buys at or after its end, derive `end_ms` from the immutable sale configuration and attach `timestamp_window(..end_ms)` in the program. Use `timestamp_window(end_ms..)` for an action that must not occur before the end. A client timeout alone is insufficient. A saved-clock upper-bound assertion alone can admit a buy whose inclusion block is already past the end. Basis: [block application order](https://github.com/logos-blockchain/logos-execution-zone/blob/1806e873ea2ac0e1b608aa7cf2f9b6e1fb12db21/lez/chain_state/src/apply.rs#L149-L258), [window API and semantics](https://github.com/logos-blockchain/logos-execution-zone/blob/578ce58a71b79c49d48e97e51c520bf71f0252d9/lee/state_machine/core/src/program/mod.rs#L476-L499), [bounds](https://github.com/logos-blockchain/logos-execution-zone/blob/1806e873ea2ac0e1b608aa7cf2f9b6e1fb12db21/lee/state_machine/core/src/program/mod.rs#L588-L592).
- For weighted-sale pricing, first select the time contract. Pricing from a proposed `t` with an exact canonical clock assertion gives saved-clock pricing, not inclusion-header pricing. It can require retries across ticks. The `cooldown` example proves the pattern's shape, not its live success rate. Basis: [example](https://github.com/logos-blockchain/logos-execution-zone/blob/1806e873ea2ac0e1b608aa7cf2f9b6e1fb12db21/test_programs/guest/src/bin/cooldown.rs#L40-L64), [clock timing](https://github.com/logos-blockchain/logos-execution-zone/blob/616256b9c9efd2c28d4f7683b7b5d2348df7314e/docs/lez-guide/src/build/system-programs.md#L40-L53).
- A different design can compute from proposed `t` and restrict inclusion to a program-defined interval around `t` with a validity window. This bounds the pricing-time error relative to the inclusion header, but lets the caller choose a favorable time within the permitted interval. Exact millisecond matching can be represented by `[t, t+1)`, with checked arithmetic, but has a severe inclusion-liveness constraint. Specify the allowed error and economic effect before using this route. Basis: [window semantics](https://github.com/logos-blockchain/logos-execution-zone/blob/1806e873ea2ac0e1b608aa7cf2f9b6e1fb12db21/lee/state_machine/core/src/program/mod.rs#L588-L626), [first-party research on the leeway trade-off](https://forum.research.logos.co/t/block-context-in-lee-a-design-exploration/666).
- An actor clock inequality proves only that inequality. It does not make an arbitrary proposed pricing time equal to current time. Use the complete canonical actor identity, check seconds-to-milliseconds conversion, and add the sale's inclusion-time deadline independently when that is the selected deadline rule. Basis: [canonical actor assertion example](https://github.com/logos-blockchain/logos-execution-zone/blob/1806e873ea2ac0e1b608aa7cf2f9b6e1fb12db21/test_programs/guest/src/bin/cooldown.rs#L58-L64), [inclusive clock assertion](https://github.com/logos-blockchain/logos-execution-zone/blob/1806e873ea2ac0e1b608aa7cf2f9b6e1fb12db21/lez/programs/clock/src/main.rs#L67-L74), [timestamp unit](https://github.com/logos-blockchain/logos-execution-zone/blob/1806e873ea2ac0e1b608aa7cf2f9b6e1fb12db21/lee/state_machine/core/src/lib.rs#L43-L44).

## Trust limit and unanswered questions

Verified report, with a current source check: open issue #863 reports that the producer controls block time without a monotonicity or wall-clock-skew bound. The pinned and current `validate_against_tip` paths do not add those checks; the current clock checks block-ID progression, not timestamp progression. The unmerged specs also state this limit explicitly. Thus, "trusted time" currently needs a producer-time trust assumption. Neither clock assertions nor validity windows independently prove physical UTC time or bind time to Bedrock's timestamp. Sources: [issue #863](https://github.com/logos-blockchain/logos-execution-zone/issues/863), [pinned header checks](https://github.com/logos-blockchain/logos-execution-zone/blob/578ce58a71b79c49d48e97e51c520bf71f0252d9/lez/chain_state/src/apply.rs#L96-L134), [current checks](https://github.com/logos-blockchain/logos-execution-zone/blob/1806e873ea2ac0e1b608aa7cf2f9b6e1fb12db21/lez/chain_state/src/apply.rs#L100-L143), [clock update](https://github.com/logos-blockchain/logos-execution-zone/blob/1806e873ea2ac0e1b608aa7cf2f9b6e1fb12db21/lez/programs/clock/src/main.rs#L24-L41), [draft spec](https://github.com/logos-blockchain/logos-execution-zone/blob/9872dd9c6e6b87372d30a232112b362c98f7cfc3/lez-specs.md#L476).

Unanswered: the reviewed sources do not establish a wall-clock freshness bound during stalls, a production inclusion success rate for exact clock assertions, or the reason tail ordering remains necessary under actors. No live private proof, producer-skew test or weighted-sale transaction was run for this note. These checks remain required before treating the selected pricing and deadline rules as deployment evidence.
