# Launchpad proposal decisions for Logos review

This register compares the current design with the [bonding-curve proposal](https://github.com/logos-co/rfp/issues/118), the [fixed-price and weighted sale proposal](https://github.com/logos-co/rfp/issues/119), [RFP-015](https://github.com/logos-co/rfp/blob/master/RFPs/RFP-015-bonding-curve-launchpad.md) and [RFP-016](https://github.com/logos-co/rfp/blob/master/RFPs/RFP-016-lbp-launchpad.md). The decisions below are open for Logos review. The linked ADRs define the details. The [workspace guide](../architecture/workspace-guide.md#execution-and-evidence-limits) records what has been verified.

| Topic | Proposal baseline | Current decision and reason |
| --- | --- | --- |
| Namespace fee rate | RFP-016 F.2 and F.10 save the rate at creation. RFP-015 F.8 uses the current namespace rate. | Use the current namespace rate for every trade across all three sale types. One namespace policy applies to existing and new sales. A rate update changes terms for future trades on active sales, so participants need a current quote and a slippage limit. [ADR 0015](../adr/0015-fee-accounting.md) |
| Fee burden and collection | RFP-016 uses creator-borne buy fees and collects after the scheduled end. | Charge traders in collateral to keep fees separate from the balance that backs sells. Permit collection at any time to the current treasury. [ADR 0015](../adr/0015-fee-accounting.md) |
| Optional retained sell fee | The curve proposal keeps its pricing constant fixed. The fixed-price and weighted proposal focuses on buys. | Support optional sells and a creator-selected retained sell fee. It defaults to zero and stays fixed for the sale. The fee stays in reserves or recorded proceeds. In a curve sale it increases the pricing constant, so it can affect later prices. [ADR 0009](../adr/0009-curve-arithmetic.md), [ADR 0015](../adr/0015-fee-accounting.md) |
| Aggregate purchase limit | The fixed-price and weighted proposal includes a per-block ceiling. The curve proposal does not include it. | Offer the same optional cap on total launch-token buy output per block for all three sale types. It limits accumulation speed without tracking buyers across accounts. A capped buy must enter the next block after its clock read, which adds a timing constraint for the planned private route. [ADR 0021](../adr/0021-modes-and-open-limits.md#per-block-allocation-ceilings) |
| Sale closing and payouts | The curve proposal describes sellout, optional expiry, and creator withdrawal. RFP-016 F.5 ties withdrawal to scheduled end. | Use immutable ending policies supported by each sale type. Settlement follows the selected ending policy. Scheduled-only sales wait for expiry even after sellout. Use the same settlement route rules across all engines. [ADR 0025](../adr/0025-sale-closing.md), [ADR 0020](../adr/0020-settlement-and-graduation.md) |
| Minimum curve duration | The curve proposal lists an enforced minimum under Soft-3. RFP-015 ties it to the time private buyers need. Neither says five minutes. | PR #56 introduced a five-minute floor. [PR #59](https://github.com/bleu/logos-launchpad/pull/59) proposes to defer the minimum until the private route works and proof and inclusion latency can be measured. Short public sales would be possible during the deferral. Expiry and closed-pool recovery still apply. [ADR 0025](../adr/0025-sale-closing.md) |
| Sale inputs and allocations | The curve proposal describes deposited allocations and a DEX seed reserve. | Use typed creation inputs and derive exact supply from sale inventory, the protected graduation reserve, and creator allocation. This keeps additional allocations out of pricing and prevents edits during resumed setup. [ADR 0007](../adr/0007-typed-sale-inputs.md), [ADR 0008](../adr/0008-curve-allocation-and-close.md), [ADR 0020](../adr/0020-settlement-and-graduation.md#graduation-reserve) |
| Graduation | The curve proposal describes a DEX target and a manual withdrawal path while that integration is pending. | Use a common adapter contract and immutable payout shares across all engines. Ship a plain-transfer distribution adapter first. A configured adapter is the required payout route. A live liquidity adapter remains deferred until compatible services exist. [ADR 0020](../adr/0020-settlement-and-graduation.md), [ADR 0036](../adr/0036-graduation-adapter-delivery.md) |
| Private trade and recovery | Both proposals describe three transactions with recovery after an interrupted return. | The planned SDK route funds the trade, executes it, and returns assets in one transaction. Atomic returns prevent a successful trade from leaving funds public. The full route and live timing are still pending. [ADR 0018](../adr/0018-private-participation.md) |
| Allowlist and repeat buys | The weighted proposal describes private membership with a sale-scoped nullifier. | Verify public Merkle paths against the actual approved trading account and permit repeat buys. This keeps verification bounded and avoids tracking consumed credentials. The used public account and membership data are visible. [ADR 0021](../adr/0021-modes-and-open-limits.md) |
| Weighted clock and poke | The weighted proposal describes lazy weight updates and a permissionless poke. | Price from the authenticated upstream clock and report weight checkpoints as observations. The checkpoint cannot change pricing or settlement. [ADR 0026](../adr/0026-lbp-clock-and-poke.md) |
| Pause and emergency freeze | The weighted proposal describes creator pause alongside the platform freeze integration. | Save an immutable pause policy for each sale. Separate creator pause from namespace emergency freeze so either control can stop trades without changing the sale schedule. [ADR 0021](../adr/0021-modes-and-open-limits.md), [ADR 0028](../adr/0028-token-custody-and-freeze.md) |
| Event retention | LP-0012 calls for retention of events emitted before a failure. | Keep only events from committed changes. Failed transactions roll back sale state and sale events together. [ADR 0027](../adr/0027-events-and-history.md) |
| Repository and weighted math | Both bids describe standalone builds and reference a separately published weighted math crate. | Maintain all sale types and clients in one repository. Keep weighted math in an independent workspace inside it so math and sale changes can be reviewed together without a separate package release. The kernel remains unaudited. [ADR 0001](../adr/0001-monorepo.md), [ADR 0002](../adr/0002-in-repo-weighted-math.md) |
| Platform interfaces | Both proposals specify SPEL interfaces and upstream token and wallet tooling. | Target one pinned LEZ actor revision and generate actor IDLs. Use temporary compatibility components where upstream coverage is missing. Replace them as compatible upstream components become available. [ADR 0034](../adr/0034-lez-v04-migration.md) |

Private participation, native proofs, Basecamp package loading, and live deployment checks remain delivery work. See the [workspace guide](../architecture/workspace-guide.md#execution-and-evidence-limits).
